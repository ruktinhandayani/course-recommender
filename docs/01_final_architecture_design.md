# CRE Final Architecture Design

## 1. Purpose

CRE is a Moodle integration prototype for displaying course recommendations generated by an external ML recommender service.

The project contribution is not the ML algorithm and not the Moodle LMS itself. The contribution is the integration architecture that turns external ML recommendation candidates into valid, secure, cached, displayable Moodle course recommendations.

## 2. Locked Architecture Decision

Use a semi-offline integration architecture:

```text
ML nightly batch
    -> Moodle scheduled/manual sync
    -> Moodle recommendation cache
    -> Dashboard block reads cache
```

The Moodle dashboard must not call the ML service directly. Moodle login must not call the ML service directly.

## 3. Component Overview

```text
Cleaned Dataset
users.csv, courses.csv, interactions.csv, course_alias_map.csv
        |
        | model training / batch generation
        v
ML Recommendation Service
- runs scheduled batch recommendation generation
- stores pre-generated recommendation candidates
- exposes paginated export API
        |
        | signed paginated API pull
        v
Moodle local_courserecommender
- imports cleaned dataset
- maps canonical_course_id to Moodle course id
- validates recommendation candidates
- stores valid recommendation cache
- logs sync and skip reasons
- exposes CLI/admin diagnostics
        |
        | database read
        v
Moodle block_courserecommender
- dashboard UI
- displays top-3 cached recommendations
- never calls ML service
```

## 4. Responsibility Split

### 4.1 ML Recommendation Service

Responsibilities:

```text
- load model artifacts or pre-generated recommendation output
- run scheduled recommendation generation, e.g. midnight batch
- store recommendation candidates internally
- expose paginated export endpoint
- expose optional per-user debug endpoint
- return user_id, canonical_course_id, rank, score, model_version, generated_at
```

Non-responsibilities:

```text
- Moodle internal course ids
- Moodle permissions
- Moodle course visibility
- Moodle completion status
- dashboard rendering
```

### 4.2 Moodle local_courserecommender

Responsibilities:

```text
- create plugin tables
- seed/import cleaned dataset
- seed Moodle demo users/courses for evaluation
- call ML export API
- validate API response
- map canonical_course_id to moodle_courseid
- check user/course display eligibility
- cache valid recommendations
- keep old cache if sync fails
- log sync results and skip reasons
- provide scheduled task, CLI runner, and admin diagnostics
- implement basic Moodle privacy provider
```

### 4.3 Moodle block_courserecommender

Responsibilities:

```text
- read active cached recommendations
- display top-3 valid recommendations
- show empty/stale state
- link to Moodle course page
```

Non-responsibilities:

```text
- ML API calls
- heavy validation
- data seeding
- sync execution
```

## 5. Moodle Plugin Strategy

Use two plugins:

```text
local_courserecommender
block_courserecommender
```

The local plugin is used because Moodle local plugins are appropriate for site-level functionality and integration logic. The block plugin is used because Moodle block plugins are appropriate for dashboard/sidebar presentation.

Official Moodle references:

```text
- Local plugins: https://moodledev.io/docs/5.0/apis/plugintypes/local
- Block plugins: https://moodledev.io/docs/5.0/apis/plugintypes/blocks
- Task API: https://moodledev.io/docs/5.0/apis/subsystems/task
- Privacy API: https://moodledev.io/docs/5.0/apis/subsystems/privacy
```

## 6. Identity and Mapping Decisions

### 6.1 User Identity

Use dataset `user_id` as the employee identifier.

For seeded Moodle users:

```text
mdl_user.username = user_id
mdl_user.idnumber = user_id
local_cr_users.user_id = user_id
local_cr_users.moodle_userid = mdl_user.id
```

Do not force `user_id` into Moodle internal `mdl_user.id`.

Reason:

```text
mdl_user.id is Moodle-owned internal database identity.
employee user_id is external business identity.
```

### 6.2 Course Identity

Use `canonical_course_id` as the integration course identifier.

Mapping:

```text
canonical_course_id -> mdl_course.id
```

Do not use course names as identifiers because names can change, duplicate, or differ in capitalization.

Do not expose Moodle internal `course.id` to the ML service.

## 7. Recommendation Rules

The ML service produces candidate recommendations. Moodle decides which candidates are displayable.

Validation rules:

```text
1. user exists in local_cr_users and Moodle
2. canonical_course_id is mapped
3. mapped Moodle course exists
4. Moodle course is visible
5. user has not completed the course
6. user is not already enrolled
7. duplicate recommendation is removed or rejected
```

Decision:

```text
Only recommend new courses.
```

Reason:

```text
Already enrolled courses are already handled by Moodle's My courses / Course overview area, so showing them again in CRE is redundant.
```

Official Moodle user-facing reference:

```text
Course overview: https://docs.moodle.org/en/Course_overview
```

## 8. Ranking and Display

ML rank is preserved.

Process:

```text
1. Receive candidates ordered by ML rank.
2. Filter invalid candidates.
3. Sort remaining candidates by original ML rank.
4. Display top-3 valid candidates.
```

The system does not re-rank candidates in Moodle.

Score display:

```text
Match score: 92%
```

The score is display/ranking metadata from the ML service. It should not be described as a guaranteed probability of course completion or learning success.

Recommendation reason text:

```text
Pending.
```

The current ML model does not explain recommendation reasons. The UI should not fake explanations. `reason_code` may be stored as nullable for future use.

## 9. Sync Architecture

Use paginated bulk export as the main sync path.

Main API:

```http
GET /recommendations/export?model_version=latest&cursor={cursor}&limit=1000
```

Optional debug API:

```http
GET /recommendations/user/{user_id}
```

Pagination size:

```text
limit = 1000 rows per page
```

Top-K candidate count:

```text
top_k = 20 per user
```

Reason:

```text
Moodle may filter some candidates. Top-20 gives enough candidates to still display top-3 valid recommendations after filtering.
```

## 10. Sync Atomicity

A sync run must be atomic from the dashboard perspective:

```text
A failed sync must not wipe or corrupt the previous active recommendation cache.
```

Staged sync process:

```text
1. Create sync_run_id.
2. Fetch paginated recommendation export.
3. Validate and map each candidate.
4. Insert valid new recommendations as inactive/pending.
5. Log skipped candidates with skip reasons.
6. If all pages succeed:
   - deactivate old active rows for affected users
   - activate new valid rows for sync_run_id
   - mark sync run as success
7. If any critical error occurs:
   - mark sync run as failed
   - keep previous active cache untouched
   - leave pending rows inactive or remove them
```

Dashboard query rule:

```text
Read only is_active = 1 recommendations.
```

## 11. Cache Freshness

MVP decision:

```text
stale_after_hours = 24
no hard expiry
```

Behavior:

```text
fresh cache:
- display normally

stale cache:
- display recommendations with "Last updated ..." or stale indicator

missing cache:
- show empty state
```

## 12. Security Architecture

### 12.1 MVP Security

Implement:

```text
- API key or bearer token
- HMAC signature
- timestamp anti-replay
- request_id / sync_run_id tracing
- HTTP timeout
- sanitized logs
- secrets stored in Moodle config / environment variables, not hardcoded
```

### 12.2 Production Security Extension

Document as future/production design:

```text
- private VPC
- security group allows ML access only from Moodle server
- TLS or mTLS
- nonce replay protection
- secret rotation
```

## 13. Privacy Provider

The local plugin stores user-related learning and recommendation data, so it should implement a simple Moodle privacy provider.

MVP privacy provider scope:

```text
- declare stored personal/user-related data
- support export of a user's recommendation data
- support deletion/anonymization of a user's recommendation data
```

The block plugin stores no personal data directly and can implement a null privacy provider if it only displays data owned by the local plugin.

## 14. Deployment Decision

Local/private deployment is acceptable.

Public internet deployment is not required for the skripsi prototype.

Reason:

```text
- the research target is integration design and evaluation
- local deployment is repeatable and measurable
- public deployment creates avoidable privacy/security risk
```

## 15. Minimum Publishable Claim

The system should prove:

```text
1. ML service exports pre-generated recommendations.
2. Moodle imports them through scheduled/manual sync.
3. Moodle maps canonical_course_id to Moodle course id.
4. Moodle filters invalid recommendations.
5. Moodle caches valid recommendations.
6. Dashboard displays top-3 from cache.
7. Dashboard does not call ML service.
8. ML failure does not break Moodle.
9. Basic API security works.
10. Evaluation results are quantitative.
```
